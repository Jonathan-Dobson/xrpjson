The field-ownership index is the union of those two sources. Merging can only
widen a field's accepted-type set, never narrow it, so no call that works today
can start failing — and the widening has a cost, recorded below.

## Protocol-only fields — the new catch surface

These 4 fields exist in the protocol but have no `XxxProps`
interface in this library. Using one on the **wrong** transaction is caught by
the index and rejected at construction. Using one on the transaction that
**owns** it is accepted and passed through unvalidated, because this library
has no guard for a field it does not model — the ledger rejects it later, with
a less specific message.

## Why these are not resolved

The union is a deliberate trade. Narrowing it — rejecting a protocol-legal
field on the transaction that owns it, because this library has no model for
it — would convert the forward-compatibility hatch into a hard failure for any
field the library has not caught up with yet. The library's rule is that a
field with no guard is caught by the ledger, not by the constructor, except
where the library deliberately chooses to model it.

A divergence of the *other* direction — modelled here, absent from the codec —
is reported but not failed on, because the codec may simply be behind the
ledger: the library can legitimately support a field the codec has not placed
yet, and that is the case the merge exists to tolerate. The library's practice
is to remove such a field rather than ship it — `a2685e7` dropped
`NFTokenBrokerFee` from `AccountSetProps` for exactly this reason, so the
ledger would not reject it with a confusing "found in disallowed location".
